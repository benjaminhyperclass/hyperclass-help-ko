# 대화 API — 연락처 ID로 수신 메시지 추가

수신 메시지 추가 기능을 쓰면 대화 ID를 먼저 찾지 않고도 연락처 ID만으로 **대화**에 수신 메시지를 등록할 수 있어요. API 호출이 줄고 로직이 단순해지며, 메시지가 CRM의 알맞은 스레드에 들어가요. 이 문서에서는 장점, 설정, 페이로드 구조, 스레드 연결 규칙, 권장 사항을 알려 드려요.

{% hint style="warning" %}
하이퍼클래스 CRM 플랫폼의 전체 REST API 문서는 API 문서의 "Send a new message"(새 메시지 보내기) 항목에서 확인할 수 있어요.
{% endhint %}

---

## 수신 메시지 추가(연락처 기반)란?

수신 메시지 추가는 연락처 ID를 받아 새 **수신(inbound)** 메시지를 알맞은 대화에 등록해요. 기존 스레드에 이어 붙이거나 새 스레드를 만들어요. 제공업체, 웹훅, 가져오기 등에서 연락처를 이미 알고 있는 상태로 메시지를 받아올 때 더 빠르고 안정적으로 연동할 수 있어요.

- 연락처 ID, 채널, 내용을 보내면 스레드 연결은 시스템이 알아서 처리해요.
- 조건에 맞는 대화가 있으면 그 대화에 메시지를 추가하고, 없으면 새 대화를 만들어요.
- SMS/MMS, 이메일, WhatsApp, 메신저, Instagram, 웹 채팅 같은 주요 채널에서 쓸 수 있어요.

## 수신 메시지 추가의 장점

아래 장점은 네트워크 왕복 횟수 감소, 더 명확한 개발 흐름, CRM에서의 더 나은 상담 환경으로 이어져요.

- API 호출 감소: 일반적인 수신 흐름에서 대화를 조회하거나 만드는 호출이 필요 없어요.
- 단순한 흐름 제어: "대화가 있을 때와 없을 때"로 나누는 분기를 줄일 수 있어요.
- 깔끔한 CRM 사용 경험: 메시지가 알맞은 스레드에 자동으로 들어가요.
- 더 안정적인 연동: 호출이 적으면 일시적으로 실패할 지점도 줄어요.
- 하위 호환: 기존의 대화 ID 방식도 그대로 동작해요.

## 엔드포인트와 페이로드 개요 (개념 설명)

아래 예시는 요청을 만들고 응답을 읽는 방법을 보여 줘요. 필드 이름은 대표적인 예시예요. 실제 구현은 사용 중인 환경의 최신 개발자 문서에 맞춰 주세요.

HTTP

```
POST /conversations/inbound-messages
Authorization: Bearer <token>
Content-Type: application/json
```

요청 (대표 예시)

```
{
  "contactId": "CONTACT_ID",
  "channel": "sms | whatsapp | email | messenger | instagram | webchat",
  "endpoint": {
    "phone": "+15551234567",
    "email": "user@example.com"
  },
  "content": {
    "text": "Hello from our provider",
    "attachments": [
      {
        "type": "image|file|video",
        "url": "https://example.com/file.jpg",
        "filename": "file.jpg",
        "sizeBytes": 123456
      }
    ]
  },
  "metadata": {
    "providerMessageId": "ext-abc-123",
    "externalThreadKey": "optional-correlation",
    "timestamp": "2026-02-04T10:15:30Z"
  },
  "idempotencyKey": "fd2d5f6f-5a9f-4b0a-8d68-0d5f6a1c9e5a"
}
```

응답 (대표 예시)

```
{
  "messageId": "MSG_123",
  "conversationId": "CONV_987",
  "contactId": "CONTACT_ID",
  "channel": "sms",
  "direction": "inbound",
  "createdAt": "2026-02-04T10:15:31Z"
}
```

## 스레드 연결 규칙

스레드 연결 규칙에 따라 메시지가 기존 대화에 추가될지, 새 대화가 만들어질지 정해져요. 이 규칙을 알아 두면 스레드가 중복되거나 쪼개지는 일을 막을 수 있어요.

- 기존 스레드(같은 채널): 연락처에게 같은 채널의 `open`(열린) 대화가 있으면 그 스레드에 메시지를 추가해요.
- 알맞은 스레드가 없을 때: 시스템이 새 대화를 만들고, 응답에 `conversationId`를 담아 돌려줘요.
- 연락처에 엔드포인트가 여러 개일 때: 같은 채널에 주소가 여러 개(전화번호 둘, 이메일 둘 등)라면 `endpoint.phone`이나 `endpoint.email` 같은 엔드포인트 힌트를 함께 보내 어느 주소인지 구분해 주세요.
- 여러 로케이션이 있을 때: 연락처가 여러 로케이션에 있다면, 인증 정보나 페이로드가 올바른 로케이션/워크스페이스를 가리키는지 확인하세요.
- 보관·종료된 스레드: 종료되거나 보관된 스레드만 있으면 새 대화를 만들어요.

## 설정과 준비 사항

인증 정보, 스코프, 환경 정보를 미리 준비해 두면 연동이 더 안정적이고 빨라져요.

- 접근 권한과 스코프: API 접근 권한이 있는지, 내 역할에 필요한 대화/연락처 스코프가 있는지 확인하세요.
- 인증: 사용 중인 환경의 기준에 맞춰 OAuth 또는 API 키를 쓰세요.
- 연락처 확인: 전화번호나 이메일 일치 여부 등으로 연락처 ID를 안정적으로 가져오거나 검증하는 방법을 앞단에 마련해 두세요.
- 로케이션 정보: 호출은 연락처와 대화 데이터를 가진 올바른 로케이션을 가리켜야 해요.

## 채널별 유의 사항과 첨부파일

채널마다 적용되는 규칙이 달라요. 전송 실패나 업로드 거부를 막으려면 페이로드를 미리 확인하세요.

- SMS/MMS: 글자 수와 미디어 크기·형식 제한을 지키세요. 시스템이 접근할 수 있는 미디어 URL을 쓰는 것이 좋아요.
- WhatsApp: 템플릿과 자유 형식 메시지 제약을 지키고, 미디어 형식이 WhatsApp 사양에 맞는지 확인하세요.
- 이메일: 올바른 MIME 유형을 지정하세요. 텍스트/HTML 본문과 첨부파일을 지원해요.
- 메신저/Instagram: 각 플랫폼의 API 제한과 호출 횟수 제한이 적용될 수 있어요. 미디어 크기(가로·세로)도 확인하세요.
- 웹 채팅: 지원하는 리치 콘텐츠는 위젯 기능에 따라 달라요. 필요하면 텍스트로 대체하세요.

## 멱등성, 재시도, 호출 제한

네트워크 오류나 제공업체의 시간 초과는 흔히 일어나요. 멱등성 키와 체계적인 재시도 로직을 쓰면 메시지 중복을 막고 사용자 신뢰를 지킬 수 있어요.

- 멱등성: 항상 `idempotencyKey`를 포함하세요. 같은 키로 재시도하면 중복 메시지가 생기지 않아야 해요.
- 재시도 정책: `5xx` 오류나 시간 초과가 나면 지수 백오프(exponential backoff)로 재시도하세요. `429` 응답이 오면 이를 따르고, `Retry-After` 헤더가 있으면 그 값도 지키세요.
- 추적: 요청 ID와 `providerMessageId`를 로그에 남겨 하위 시스템과 대조할 수 있게 하세요.

---

## 오류 처리와 주요 응답

오류 처리 방식을 통일해 두면 원인을 찾는 시간이 줄고, 사용자에게 보이는 불일치도 막을 수 있어요.

- 400 Bad Request — 잘못된 `contactId`, 누락된 `channel`, 잘못된 형식의 내용, 지원하지 않는 첨부파일 유형 또는 크기
- 401/403 — 인증 실패, 또는 해당 로케이션에 대한 스코프나 역할 권한 부족
- 404 Not Found — `contactId`를 찾을 수 없거나 현재 로케이션에서 보이지 않음
- 409 Conflict — 멱등성 키 충돌 또는 중복 제출 감지
- 413 Payload Too Large — 첨부파일이 크기 제한 초과
- 429 Too Many Requests(요청이 너무 많습니다) — 호출 제한 초과. 잠시 기다린 뒤 재시도하세요.
- 5xx — 제공업체나 시스템의 일시적 오류. 같은 `idempotencyKey`로 재시도하세요.

## 테스트와 검증

운영에 적용하기 전에 반복 가능한 테스트 계획을 세워 두면, 메시지가 올바르게 스레드에 연결되고 CRM에 제대로 표시되는지 확인할 수 있어요.

- 기본 시나리오: 알고 있는 `contactId`로 수신 메시지를 보내고, 알맞은 대화에 나타나는지 확인하세요.
- 스레드가 없는 경우: 열린 대화가 없는 연락처로 보내고, 새 `conversationId`가 돌아오는지 확인하세요.
- 엔드포인트가 모호한 경우: 전화번호나 이메일이 여러 개인 연락처로 테스트하세요. 엔드포인트 힌트를 포함해 스레드가 올바르게 연결되는지 확인하세요.
- 첨부파일: 허용되는 미디어를 보내 보고, CRM 타임라인에 제대로 표시되는지 확인하세요.
- 복원력: 시간 초과 상황을 만들어, 멱등성 키를 쓴 재시도가 중복을 만들지 않는지 확인하세요.

## 자주 묻는 질문

### 대화 ID로도 수신 메시지를 등록할 수 있나요?
네, 가능해요. 기존 방식도 계속 지원해요. 연락처 기반 수신은 추가된 간편 방식이에요.

### 채널을 빼고 보내면 어떻게 되나요?
요청이 거부돼요. `channel`을 꼭 넣고, 필요하면 주소를 구분할 수 있는 `endpoint` 필드도 함께 보내세요.

### 스레드가 여러 개일 때 어떤 대화가 선택되나요?
같은 채널의 열린 스레드를 우선해서 선택해요. 없으면 새 대화를 만들어요.

### 시간 초과 뒤 재시도할 때 중복은 어떻게 막나요?
모든 요청에 `idempotencyKey`를 넣고, 재시도할 때도 같은 키를 다시 쓰세요.

### 과거 수신 메시지를 뒤늦게 채워 넣을 수 있나요?
네, 가능해요. `metadata.timestamp`에 원래 시각을 넣으면 메시지가 타임라인에서 그 시각 순서대로 정렬돼요.

### 연락처가 여러 로케이션에 있을 때 올바른 로케이션을 지정하려면 어떻게 하나요?
대상 로케이션/워크스페이스에 연결된 인증 정보나 헤더를 쓰세요. 호출은 해당 연락처를 가진 로케이션 범위로 보내야 해요.
