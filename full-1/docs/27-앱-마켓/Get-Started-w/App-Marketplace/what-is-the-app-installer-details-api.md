# 앱 설치자 상세 정보 API(App Installer Details API)란?

앱 설치자 상세 정보 API는 마켓플레이스 개발자가 누가 앱을 설치했는지, 어느 에이전시·서브 계정에 설치했는지, 그리고 브랜딩에 쓸 에이전시 화이트라벨 데이터까지 확인할 수 있게 해 주는 API예요. 회사 단위의 넓은 OAuth 스코프를 요청하지 않고도 온보딩을 맞춤 구성하고, 앱 화면을 에이전시 브랜딩에 맞추고, 에이전시 소유자와 소통할 수 있어요. 덕분에 사용자 유지율이 높아지고 설정이 빨라지며, 화이트라벨이 그대로 지켜져요.

## 앱 설치자 상세 정보 API 소개

이 API는 마켓플레이스 앱을 설치한 사용자에 대한 검증된 정보와, 앱이 설치된 정확한 위치(서브 계정과 에이전시)를 돌려줘요. 에이전시 프로필과 화이트라벨 데이터도 함께 제공해요. 그래서 회사 단위의 넓은 OAuth 스코프를 요청하지 않고도 온보딩, 브랜딩, 커뮤니케이션을 맞춤 구성할 수 있어요.

이 엔드포인트는 다음이 필요한 마켓플레이스 개발자를 위해 만들어졌어요.

- 설치한 사용자를 식별해야 할 때
- 화이트라벨 경계를 지켜야 할 때
- 에이전시와 서브 계정에 맞게 앱 경험을 조정해야 할 때

---

## 주요 장점

설치자 정보를 가져온 뒤 무엇을 자동화할지 정할 때 아래 항목을 체크리스트로 활용해 보세요.

- 신원과 위치 파악: 설치한 사용자와 앱이 있는 위치(서브 계정과 에이전시)를 알 수 있어요.
- 화이트라벨 반영: 에이전시의 화이트라벨 필드로 앱 브랜딩을 맞출 수 있어요.
- 스코프 최소화: 에이전시 정보를 읽으려고 회사 단위의 넓은 OAuth 스코프를 요청하지 않아도 돼요.
- 맞춤 온보딩: 에이전시별 환영 흐름, 콘텐츠, 가격을 구성할 수 있어요.
- 소유자와 직접 소통: 에이전시 소유자 정보가 포함되어 있어, 유지율을 높이는 직접적인 관계를 만들 수 있어요.
- 개인정보 보호 설계: 서브 계정에 상위 에이전시의 브랜딩이 노출되지 않도록 화이트라벨을 지켜요.

---

## 인증 방식

어떤 토큰을 쓰느냐에 따라 API가 확인하는 범위가 달라져요. 최소 권한 원칙과 마켓플레이스 정책에 맞게 어떤 토큰을 쓸지 아래를 참고하세요.

- 지원하는 토큰: 에이전시 토큰 또는 서브 계정 토큰
- 토큰별 동작
  - 에이전시 토큰으로 호출하면 설치자와 에이전시 정보를 확인해요. 해당하는 경우 설치가 이루어진 서브 계정도 알 수 있어요.
  - 서브 계정 토큰으로 호출하면 설치자와, 현재 서브 계정이 속한 에이전시 정보를 확인해요.
- 헤더 예시
  - `Authorization`: Bearer {YOUR\_TOKEN} <!-- 검토 필요: 원문에는 Authorisation 으로 표기됨 -->
  - `Content-Type`: application/json
- 최소 권한 팁: 현재 실행 환경에 맞는 토큰을 쓰세요. 예를 들어 서브 계정 워크플로우에서는 서브 계정 토큰을 쓰는 것이 좋아요.

{% hint style="info" %}
필요한 권한은 마켓플레이스 기준을 따라요. 설치 정보를 읽을 수 있는 가장 낮은 권한의 토큰을 쓰세요. 브랜딩 정보를 얻으려는 목적만으로 넓은 에이전시 스코프를 요청하지 마세요.
{% endhint %}

## 엔드포인트와 요청 예시

구체적인 예시가 있으면 연동 시간이 줄어요. 아래 자리표시자는 공식 API 레퍼런스에서 확인한 실제 기본 URL과 엔드포인트 경로로 바꿔 쓰세요.

- HTTP 메서드: GET
- 엔드포인트 경로: `/marketplace/app-installer/details` (자리표시자예요. 정확한 경로는 [공식 API 문서](../../../35-개발자/Developer-Resources/hyperclass-api-documentation.md)에서 확인하세요.)

```
cURL
curl -X GET \ "{BASE_URL}/marketplace/app-installer/details" \ -H "Authorization: Bearer {AGENCY_OR_SUB_ACCOUNT_TOKEN}" \ -H "Content-Type: application/json"
```

## 응답 스키마(필드 참조)

필드별 설명을 보면 데이터를 시스템에 안전하게 매핑할 수 있어요. null이 될 수 있는 필드와 선택 항목인 화이트라벨 속성은 값이 없을 수 있다고 가정하고 처리하세요.

주요 필드(대표 예시예요. 이름과 타입은 공식 문서에서 확인하세요)

- `installer.userId` (string) — 설치를 진행한 사용자의 고유 ID
- `installer.name` (string) — 사람이 읽을 수 있는 이름
- `installer.email` (string) — 협업과 계정 연결을 위한 연락처
- `installationContext.subAccountId` (string|null) — 앱이 설치된 서브 계정
- `installationContext.agencyId` (string) — 상위 에이전시 ID
- `agency.companyName` (string) — 에이전시의 법인명 또는 브랜드명
- `agency.companyEmail` (string) — 대표 연락 이메일
- `agency.ownerName` (string) — 주 소유자 또는 관리자 이름
- `whiteLabel.brandName` (string) — 화이트라벨 브랜드명
- `whiteLabel.supportEmail` (string|null) — 브랜드 이름으로 보내는 커뮤니케이션용 지원 메일함
- `whiteLabel.supportUrl` (string|null) — 도움말 센터 또는 티켓 시스템 URL
- `whiteLabel.primaryDomain` (string|null) — 브랜드 앱 또는 도메인
- `whiteLabel.logoUrl` (string|null) — UI 테마에 쓸 브랜드 로고
- `whiteLabel.faviconUrl` (string|null) — 브라우저 브랜딩용 파비콘

---

## 화이트라벨 데이터 사용 가이드

화이트라벨을 지키는 것은 하이퍼클래스 환경에서 가장 기본적인 기대 사항이에요. 에이전시 브랜딩은 사용자 경험을 높이는 데 쓰되, 상위 에이전시의 정체가 최종 고객에게 드러나지 않게 주의하세요.

- `whiteLabel.brandName`, `logoUrl`, `primaryDomain`을 사용해 에이전시 사용자용 앱 UI 테마를 구성하세요.
- 의도한 경우가 아니라면 서브 계정의 최종 고객에게 에이전시 정체가 드러나지 않게 하세요.
- 브랜딩 필드는 서버에서 짧은 TTL(예: 15~60분)로 캐시하세요. API 호출이 줄고 변경 사항도 반영할 수 있어요.
- 브랜딩이 바뀌면 새로운 `logoUrl` 또는 `brandName`이 감지될 때 캐시를 무효화하세요.

---

## 호출 제한과 캐싱

호출 제한과 캐싱을 미리 대비하면 앱이 안정적으로 동작해요. 일시적인 오류에는 지수 백오프를 쓰고, 캐싱으로 중복 호출을 줄이세요.

- 권장 캐싱: 설치자와 화이트라벨 결과를 토큰·컨텍스트별로 캐시하고, 로그인이나 세션을 시작할 때 새로 고치세요.
- 백오프 전략: 429 또는 5xx 응답이 오면 지터(jitter)를 넣어 백오프하고, 정해진 횟수만 재시도하세요.
- 클라이언트 관리: 페이지마다 이 엔드포인트를 호출하지 마세요. 세션당 한 번, 또는 컨텍스트가 바뀔 때만 가져오세요.

---

## 오류 처리

오류 상황을 미리 예상해 두면 개발 속도가 빨라지고 사용자 신뢰도 높아져요. API 오류를 UI에서 안내할 수 있는 메시지로 연결하세요.

| HTTP | 예상 원인 | 오류 본문 예시 | 권장 조치 |
| --- | --- | --- | --- |
| 401 | 토큰이 없거나 유효하지 않음 | { "error": "unauthorized" } | 토큰을 갱신하고 헤더 형식을 확인하세요 |
| 403 | 해당 컨텍스트에 대한 권한이 토큰에 없음 | { "error": "forbidden" } | 알맞은 에이전시 토큰 또는 서브 계정 토큰을 사용하세요 |
| 404 | 해당 컨텍스트에 앱이 설치되어 있지 않음 | { "error": "not\_found" } | 설치를 안내하거나 올바른 계정으로 전환하도록 안내하세요 |
| 429 | 호출 제한 초과 | { "error": "rate\_limited" } | 백오프와 캐싱을 적용하세요 |
| 5xx | 일시적인 서비스 문제 | { "error": "server\_error" } | 지수 백오프로 재시도하세요 |

## 버전과 제공 현황

현재 상태와 제공 단계를 알아 두면 배포를 계획하고 업그레이드 때 놀라는 일을 줄일 수 있어요.

- 상태: 새로 추가된 마켓플레이스 API 엔드포인트예요.
- 호환성: 에이전시 토큰 또는 서브 계정 토큰으로 호출하는 마켓플레이스 앱을 대상으로 해요.
- 버전 관리: API 버전 헤더나 URL 경로 구분(예: `Accept-Version`, `/v{n}` 경로)이 공개되면 조직의 방식에 따라 적용하세요. 자리표시자는 API 레퍼런스의 공식 값으로 바꾸세요.

## 앱에 설정하기

아래 순서대로 하면 엔드포인트를 빠르고 안전하게 연동할 수 있어요. 운영 환경으로 넘어가기 전에 개발 환경에서 모든 단계를 마치세요.

### 1단계: 토큰 확인

- 테스트용으로 에이전시 토큰과 서브 계정 토큰을 각각 만드세요.
- 토큰은 볼트나 시크릿 매니저에 안전하게 보관하세요. 소스 코드 저장소에는 절대 올리지 마세요.

### 2단계: 요청 추가

- `{BASE_URL}/marketplace/app-installer/details`(자리표시자 경로)로 GET 호출을 구현하세요.
- `Authorization: Bearer {TOKEN}` 헤더를 포함하세요.

### 3단계: 응답 매핑

- `installationContext`와 에이전시 ID를 저장하고, `whiteLabel` 필드는 캐시하세요.
- `whiteLabel` 값으로 UI 테마를 구성하고, 설치자 이름을 환영 문구에 활용하세요.
- [스크린샷 추가: “관리자 UI – 적용된 브랜딩(로고 + 브랜드명) 미리보기”]

### 4단계: 오류 처리와 재시도

- 401, 403, 404, 429 처리 로직과 지수 백오프를 구현하세요.
- 내부 사용자에게는 조치할 수 있는 메시지를 보여 주세요. 최종 고객에게는 원본 JSON을 노출하지 마세요.

### 5단계: 화이트라벨 유지 확인

- 서브 계정에서 에이전시 브랜딩이 의도하지 않은 대상에게 노출되지 않는지 확인하세요.

### 6단계: 모니터링과 함께 배포

- 호출 성공률, 지연 시간, 캐시 적중률 지표를 추가하세요.

## 자주 묻는 질문

### 에이전시 토큰과 서브 계정 토큰 중 어떤 걸 써야 하나요?
현재 실행 컨텍스트에 맞는 토큰을 쓰세요. 에이전시 토큰은 에이전시와 설치자 정보를 확인하고, 서브 계정에 설치된 경우도 참조할 수 있어요. 서브 계정 토큰은 현재 로케이션이 속한 에이전시 정보를 확인해요.

### 이 엔드포인트를 쓰려면 회사 단위 OAuth 스코프가 필요한가요?
아니요. 에이전시 정보를 읽으려고 회사 단위의 넓은 스코프를 요청하지 않아도 되는 것이 이 API의 큰 장점이에요.

### 화이트라벨 필드는 보통 어떤 값이 오나요?
브랜드명, 지원 이메일·URL, 브랜드 도메인, 그리고 로고와 파비콘 같은 선택 자산이 와요. 모든 필드는 값이 없을 수 있다고 보고, 짧은 TTL로 캐시하세요.

### 응답을 캐시해도 되나요?
네. 토큰·컨텍스트별로 캐시하고, 세션이 시작될 때나 브랜딩이 바뀐 것을 감지했을 때 새로 고치세요.

### 설치한 사용자가 에이전시를 떠나면 어떻게 되나요?
에이전시와 서브 계정 컨텍스트는 그대로 유지될 것으로 보면 돼요. 설치자 기록에는 당시 사용자 정보가 남아 있을 수 있어요. null이나 알 수 없는 값도 문제없이 처리하세요.

### 페이지네이션이 있나요?
아니요. 이 엔드포인트는 현재 토큰에 대한 설치자 컨텍스트 하나를 돌려줘요.

### 호출 제한은 어떻게 처리하나요?
429 응답에는 지터를 넣은 지수 백오프를 쓰고, 캐싱으로 호출 빈도를 줄이세요.

### 이 정보로 에이전시 소유자에게 직접 메시지를 보내도 되나요?
네. 관계를 쌓을 수 있도록 소유자 정보가 제공돼요. 신중하게 사용하고, 개인정보처리방침을 따르세요.
