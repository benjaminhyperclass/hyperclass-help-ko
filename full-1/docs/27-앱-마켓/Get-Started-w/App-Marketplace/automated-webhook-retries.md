# 마켓플레이스 앱 웹훅 자동 재시도

하이퍼클래스 **마켓플레이스 앱**(Marketplace apps)이 보내는 웹훅이 일시적인 요청 제한(rate limit)에 걸려도 중요한 이벤트가 서버에 도착하도록, 자동 재시도 기능이 HTTP 429 응답에 한해 재시도하고 무작위 지연(지터)을 더해요. 이 문서는 마켓플레이스 개발자를 위해 새 재시도 방식이 어떻게 동작하는지, 엔드포인트를 어떻게 준비하면 좋은지 안내해요.

함께 보면 좋은 문서는 Webhook Integration Guide(웹훅 연동 가이드)예요.

## 마켓플레이스 웹훅 자동 재시도란?

**하이퍼클래스 마켓플레이스**에는 외부로 나가는 웹훅을 위한 재시도 기능이 기본으로 들어 있어요. 앱의 엔드포인트가 HTTP 429(Too Many Requests, 요청이 너무 많음)로 응답하면, 하이퍼클래스는 같은 페이로드를 최대 6번까지 일정한 간격을 두고 다시 보내요. 이때 간격에는 무작위 지터가 더해져요. 그 밖의 상태 코드(2xx 성공, 4xx/5xx 오류)는 최종 결과로 처리해요. 그래서 전달 동작을 예측하기 쉽고, 서버에 과부하가 걸리는 일도 막을 수 있어요.

- HTTP 429일 때만 재시도: 엔드포인트가 429(요청 제한) 응답을 돌려줄 때만 웹훅 전송을 다시 시도해요.
- 지터 보호: 재시도 시점을 무작위로 흩어 놓아 요청이 한꺼번에 몰리는 "thundering herd" 문제를 막고, 서버 부하를 고르게 나눠요.

## 마켓플레이스 웹훅 자동 재시도의 장점

- 신뢰성: 일시적인 요청 제한 급증 때문에 이벤트가 사라지는 일이 없어요.
- 예측 가능성: 10분 고정 간격(지터 포함)과 최대 6회 시도 제한 덕분에 최악의 지연 시간(약 1시간 10분)을 가늠할 수 있어요.
- 서버 보호: 지터가 동시에 몰리는 재시도를 막고, 인프라 전체에 부하를 고르게 나눠 줘요.
- 개발자 제어: 429가 아닌 다른 상태 코드를 반환하면 이후 재시도를 바로 멈출 수 있어요.

---

## 재시도 일정

재시도는 이전 시도 후 10분마다 일어나요. 각 간격에는 작은 의사 난수 오프셋(지터)이 더해져서 트래픽이 한꺼번에 몰리는 것을 막아요. 재시도 6번을 채우거나 429가 아닌 응답을 받으면, 둘 중 먼저 오는 쪽에서 멈춰요. 재시도가 이어질 수 있는 전체 시간은 약 1시간 10분이에요.

- 간격: 재시도 사이 10분(지터 포함)
- 최대 시도 횟수: 재시도 6회
- 전체 재시도 시간: 약 1시간 10분

### 429가 아닌 실패의 재시도 일정

429가 아닌 웹훅 실패는 이제 HTTP 429에 쓰는 고정 간격 대신 지수 백오프(exponential backoff) 방식으로 재시도해요.

429가 아닌 실패는 최대 3일까지 재시도가 이어질 수 있어요. 엔드포인트가 일시적으로 응답하지 않거나, 시간이 초과되거나, 서버 오류가 간헐적으로 나올 때 전달 신뢰성을 높여 줘요.

---

## 재시도 조건

재시도 로직은 개발자가 항상 어떻게 동작할지 알 수 있도록 일부러 좁게 설계했어요.

- 재시도하는 상태 코드: 429만 해당돼요.
- 멈추는 조건: 그 밖의 모든 상태(200, 202, 204, 4xx, 5xx 등)
- 5xx는 재시도하지 않아요: 서버 쪽 실패는 영구 실패로 처리해요. 응답하지 않는 엔드포인트에 요청이 계속 쏟아지는 것을 막기 위해서예요.
- 5xx 서버 오류는 재시도하지 않아요. 영구 실패로 처리해요.

## HTTP 429와 그 외 실패의 재시도 조건

이제 웹훅 엔드포인트가 반환한 실패 유형에 따라 재시도 동작이 달라져요.

- HTTP 429 응답은 기존 재시도 방식을 그대로 써요. 10분 고정 간격으로 약 1시간 동안 재시도해요.
- 그 밖의 웹훅 실패도 이제 재시도해요. 엔드포인트가 일시적으로 멈춘 경우, 서버 오류, 시간 초과, 일시적인 네트워크 문제가 모두 해당돼요.

<!-- 검토 필요: 원문 내용이 서로 다름 (429 재시도 시간이 위에서는 약 1시간 10분, 여기서는 약 1시간으로 적혀 있음) -->

이렇게 해서 요청 제한 외의 실패에 대한 안정성을 높이면서도, 429 응답의 기존 처리 방식은 그대로 유지해요.

---

## 지터 보호

10분 간격마다 ± N초의 무작위 지터가 적용돼요. 이 작은 차이 덕분에 여러 이벤트가 동시에 제한되더라도 재시도가 같은 순간에 몰리지 않아요. 전체 서버에서 요청 제한이 연쇄적으로 걸릴 위험이 크게 줄어들어요.

---

## 개발자는 어떻게 사용하나요?

이 기능을 잘 활용하는 방법이에요.

✅ 전달에 성공하면 200 OK를 반환하세요.

✅ 내부 처리에 실패하더라도 수신을 확인했다는 뜻으로 200 OK를 반환하세요.

❌ 오류 코드는 꼭 필요할 때만 쓰세요.

- 408 → 서버 응답이 너무 느림
- 429 → 요청이 너무 많음
- 5xx → 서버가 중단되었거나 고장 남(재시도하지 않음)

### 개발자가 알아 둘 점

이미 외부에 공유된 마켓플레이스 웹훅을 쓰고 있다면 설정을 바꿀 필요가 없어요.

이번 개선으로 달라지는 점은 다음과 같아요.

- HTTP 429 재시도 동작은 그대로예요.
- 429가 아닌 실패는 이제 지수 백오프로 자동 재시도해요.
- 429가 아닌 실패의 재시도는 최대 3일까지 이어질 수 있어요.

웹훅 엔드포인트가 일시적으로 불안정하거나 응답하지 않을 때, 복구할 시간을 더 길게 확보할 수 있어요.

## 권장 HTTP 응답 코드

요청을 받았다고 알릴 때와 속도를 늦춰 달라고 요청할 때를 구분해서 쓰는 것이 중요해요.

- 200 OK – 처리에 성공했을 때는 항상 보내세요. 작업을 비동기로 큐에 넣더라도 200을 반환해야 하이퍼클래스가 이벤트가 수신된 것으로 알아요.
- 429 Too Many Requests(요청이 너무 많음) – 하이퍼클래스의 전송 속도를 정말로 늦춰야 할 때만 반환하세요. 위에서 설명한 재시도 흐름이 시작돼요.
- 408 Request Timeout(요청 시간 초과) – 서버가 제때 요청을 처리하지 못했다는 선택적 신호예요.
- 5xx 서버 오류 – 앱 쪽에서 심각한 실패가 발생했다는 뜻이에요. 더 이상 재시도하지 않아요.

## 자주 묻는 질문

### 재시도할 때 하이퍼클래스가 중복 이벤트를 걸러 주나요?

아니요, 하이퍼클래스가 걸러 주는 것은 아니에요. 다만 재시도할 때마다 같은 deliveryId 헤더가 붙어서 가기 때문에 중복을 안전하게 무시할 수 있어요.

<!-- 검토 필요: 원문 답변이 "Yes. Each webhook attempt uses the same deliveryId header so you can safely ignore duplicates."로, 하이퍼클래스가 직접 중복을 제거한다는 뜻인지 불분명함. 원문 그대로 "예"로 수정 필요 -->

### 재시도 간격이나 횟수를 직접 바꿀 수 있나요?

지금은 바꿀 수 없어요. 10분 간격, 6회 시도 일정은 모든 앱에 똑같이 적용돼요.

### 재시도해도 제 API의 기존 요청 제한이 지켜지나요?

네. 지터와 10분 지연 덕분에 요청이 한꺼번에 몰리는 일은 줄지만, 이벤트 하나당 최대 6번의 추가 호출이 올 수 있다는 점을 감안해서 여유를 두세요.

### 엔드포인트가 404나 400을 반환하면 어떻게 되나요?

하이퍼클래스는 429가 아닌 응답을 최종 결과로 처리해요. 더 이상 재시도하지 않아요.

<!-- 검토 필요: 원문 내용이 서로 다름 (위 "429가 아닌 실패의 재시도 일정"에서는 429가 아닌 실패도 재시도한다고 함) -->

### 스테이징 환경에서는 어떻게 테스트하나요?

스테이징 엔드포인트에서 429 응답을 가짜로 반환한 뒤, 하이퍼클래스가 약 70분에 걸쳐 페이로드를 6번 다시 보내는지 확인하세요.

### 워크플로우의 **Inbound Webhook**(인바운드 웹훅) 트리거에도 영향이 있나요?

아니요. 자동 재시도는 하이퍼클래스가 외부 서버로 보내는 마켓플레이스 앱 웹훅에만 적용돼요.

### 과거 전송 로그는 어디에서 볼 수 있나요?

**Webhook Dashboard**(웹훅 대시보드)가 출시 예정이에요. 출시되면 시도별 로그를 볼 수 있어요. 그전까지는 직접 운영하는 서버 로그를 확인하세요.

### 페이로드 크기 제한이 있나요?

네. 마켓플레이스 웹훅은 256KB까지예요. 더 큰 페이로드는 잘리고 payloadTooLarge 플래그가 붙어요.

### 재시도를 끌 수 있나요?

재시도 로직은 기본으로 내장되어 있어서 앱별로 끌 수 없어요. 엔드포인트가 멱등성(idempotency)을 지키도록 설계하세요.

### 하이퍼클래스가 5xx 오류도 재시도하나요?

아니요. 5xx 응답은 내부 서버 오류로 보고, 하이퍼클래스는 바로 재시도를 멈춰요. 추가 부하 없이 원인을 조사할 수 있어요.
