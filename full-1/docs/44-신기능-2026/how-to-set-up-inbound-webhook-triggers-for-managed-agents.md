# 관리형 에이전트에 수신 웹훅 트리거 설정하기

수신 웹훅 트리거를 쓰면 외부 애플리케이션이 보낸 데이터로 관리형 에이전트를 자동 실행할 수 있어요. 이 문서에서는 수신 웹훅 트리거를 설정하고, 보안을 적용하고, 테스트하고, 실행 내역을 확인하는 방법을 안내해요.

## 관리형 에이전트의 수신 웹훅 트리거란?

수신 웹훅 트리거는 외부 애플리케이션이 고유한 웹훅 URL로 HTTP POST 요청을 보내면 관리형 에이전트를 실행해요.

예를 들어 고객이 주문하면 온라인 스토어가 주문 정보를 에이전트에 보낼 수 있어요. 그러면 에이전트가 해당 고객의 연락처를 찾아 주문 내용을 담은 메모를 만들 수 있어요.

에이전트는 설정된 지침에 따라 들어온 데이터를 읽어요.

{% hint style="info" %}
관리형 에이전트의 수신 웹훅은 워크플로우의 수신 웹훅과 달라요. 관리형 에이전트 웹훅은 에이전트를 바로 실행하며, 워크플로우처럼 필드를 매핑할 필요가 없어요. 워크플로우의 수신 웹훅은 [워크플로우 트리거 — 수신 웹훅](../07-워크플로우/workflow-trigger-inbound-webhook.md) 문서를 참고하세요.
{% endhint %}

## 수신 웹훅 트리거의 장점

수신 웹훅 트리거를 쓰면 다른 애플리케이션에서 일어난 이벤트에 관리형 에이전트가 사람의 개입 없이 대응할 수 있어요.

- 직접 연동: 별도의 워크플로우를 만들지 않고 외부 애플리케이션을 연결해요.
- 자동 데이터 처리: 에이전트가 지침에 따라 들어온 필드를 해석해요.
- 다양한 형식: JSON, 폼 데이터, XML, 일반 텍스트, 멀티파트 요청을 받을 수 있어요.
- 여러 트리거: 이벤트마다 웹훅 URL을 따로 쓸 수 있어요.
- 선택형 보안: 공유 토큰으로 들어오는 요청을 검증할 수 있어요.
- 중복 방지: 지원되는 재전송 요청이 실행을 중복해서 시작하지 않도록 막아요.
- 실행 추적: 웹훅 활동과 에이전트 결과를 확인할 수 있어요.

## 수신 웹훅 트리거가 작동하는 방식

수신 웹훅 트리거마다 고유한 URL이 있어요. 외부 애플리케이션이 이 URL로 정보를 보내면 하이퍼클래스가 게시된 관리형 에이전트를 실행해요.

작동 순서는 다음과 같아요.

1. 외부 애플리케이션이 HTTP POST 요청을 보내요.
2. 인증을 켜 둔 경우 하이퍼클래스가 요청을 검증해요.
3. 에이전트가 요청 데이터를 첫 입력으로 받아요.
4. 에이전트가 지침에 따라 데이터를 처리해요.
5. 실행 내역이 에이전트의 **활동** 탭에 표시돼요.

예를 들어 온라인 스토어가 새 주문 정보를 보내면, 에이전트가 고객을 찾아 내부 메모를 만들 수 있어요.

{% hint style="warning" %}
에이전트를 게시한 상태에서만 웹훅이 작동해요. 에이전트 게시를 취소하거나 트리거를 제거하면 해당 URL은 사용할 수 없게 돼요.
{% endhint %}

## 지원하는 요청 데이터와 제한

수신 웹훅은 여러 요청 형식을 지원해서, 관리형 에이전트가 다양한 외부 애플리케이션의 정보를 받을 수 있어요.

지원하는 형식은 JSON, 폼 데이터, XML, 일반 텍스트, 멀티파트 요청이에요.

에이전트는 요청 본문, 쿼리 매개변수, 허용된 헤더를 읽을 수 있어요.

예를 들어 에이전트에게 고객 이메일 주소가 `customer.email`에 있다고 알려 줄 수 있어요.

| 항목 | 제한 또는 동작 |
| --- | --- |
| 요청 방식 | POST |
| 최대 페이로드 | 256 KB |
| 요청 속도 | 분당 최대 60건 |
| 정상 접수 | 실행 ID(run ID)가 포함된 HTTP 202 |

{% hint style="info" %}
HTTP 202는 요청이 처리 대상으로 접수되었다는 뜻이에요. 에이전트가 작업을 끝냈다는 뜻은 아니에요. 요청 속도 제한이 어느 범위에 적용되는지는 대량 요청이 오가는 연동을 설정하기 전에 확인해야 해요.
{% endhint %}

## 웹훅 요청 보호하기

공유 토큰 검증을 쓰면 권한 없는 애플리케이션이 관리형 에이전트를 실행하지 못하게 막을 수 있어요.

검증을 켜면 요청을 보내는 애플리케이션은 아래 두 요청 헤더 중 하나에 토큰을 넣어야 해요.

- `X-Webhook-Token`
- `Authorization: Bearer`

필수 토큰이 없거나 올바르지 않은 요청은 HTTP 401로 거부돼요.

토큰은 생성할 때만 표시돼요. 필요하면 웹훅 설정에서 다시 생성할 수 있어요.

{% hint style="warning" %}
웹훅 URL과 토큰은 외부에 노출되지 않게 관리하세요. 토큰을 다시 생성했다면 외부 애플리케이션에 있는 토큰도 새로 바꿔 주세요.
{% endhint %}

## 웹훅 트리거 여러 개 관리하기

관리형 에이전트 하나에 수신 웹훅 트리거를 여러 개 만들 수 있어요. 트리거마다 이름, URL, 메시지가 따로 있어서 에이전트 하나로 여러 이벤트를 처리할 수 있어요.

예를 들면 다음과 같아요.

- 신규 주문: 새 구매를 처리해요.
- 환불 요청: 환불 요청을 검토해요.

트리거마다 알아보기 쉬운 이름을 붙이고, 들어온 데이터를 에이전트가 어떻게 처리해야 하는지 적어 주세요.

## 웹훅 활동 확인하기

에이전트의 **활동** 탭에서 요청이 제대로 들어왔는지, 에이전트가 어떻게 처리했는지 확인할 수 있어요. 활동 탭에 대한 자세한 설명은 [관리형 에이전트 활동 피드](../13-AI-Employee/Agent-Studio/managed-agent-activity-feed-monitor-debug-ai-agents.md) 문서를 참고하세요.

웹훅 실행 내역을 확인하는 방법은 다음과 같아요.

1. **AI 에이전트 > 에이전트 스튜디오**로 이동하세요.
2. 관리형 에이전트를 여세요.
3. **활동**을 선택하세요.
4. **Webhook received**(웹훅 수신) 항목을 찾으세요.
5. 실행 내역을 열어 요청 내용과 에이전트 결과를 확인하세요.

![수신된 웹훅 메시지와 실행 타임라인, 에이전트 결과 화면](https://s3.amazonaws.com/cdn.freshdesk.com/data/helpdesk/attachments/production/155083668263/original/IS981AsTvV9qZOLRgi3Fdn9wrOfqCc1lGA.png?1792418065)

## 웹훅 응답과 오류 이해하기

응답 코드를 보면 요청이 접수되었는지, 실패했다면 이유가 무엇인지 알 수 있어요.

| 상태 | 의미 | 확인할 내용 |
| --- | --- | --- |
| 202 | 요청 접수됨 | **활동**에서 실행 내역을 확인하세요 |
| 401 | 인증 실패 | 토큰과 요청 헤더를 확인하세요 |
| 404 | 웹훅을 찾을 수 없음 | 웹훅 URL이 맞는지 확인하세요 |
| 410 | 웹훅을 사용할 수 없음 | 트리거와 에이전트가 활성 상태인지 확인하세요 |
| 413 | 요청이 너무 큼 | 페이로드 크기를 줄이세요 |
| 415 | 지원하지 않는 형식 | 요청 형식과 Content-Type을 확인하세요 |
| 429 | 요청이 너무 많음 | 요청 속도를 줄이고 Retry-After 값을 따르세요 |

중복 요청: 외부 애플리케이션이 전송을 다시 시도하면, 하이퍼클래스는 멱등성 키(idempotency key), 웹훅 이벤트 ID, 또는 짧은 시간 안에 들어온 동일한 요청 본문으로 지원되는 중복 요청을 알아볼 수 있어요. 이 경우 새 실행을 만들지 않고 원래 실행을 반환해요.

## 관리형 에이전트에 수신 웹훅 트리거 설정하기

수신 웹훅 트리거를 추가하고, 지침을 설정하고, 연결을 테스트하면 외부 애플리케이션을 관리형 에이전트에 연결할 수 있어요.

아래 예시는 온라인 스토어가 새 주문 정보를 에이전트에 보내는 경우예요.

### 1단계: 관리형 에이전트 열기

1. **AI 에이전트 > 에이전트 스튜디오**로 이동하세요.
2. 기존 관리형 에이전트를 열거나 새로 만드세요.
3. 에이전트 편집기를 여세요.

### 2단계: 수신 웹훅 트리거 추가하기

1. **트리거**를 찾아 **트리거 추가**를 클릭하세요.
2. **수신 웹훅**을 선택하세요.
3. 트리거 이름을 입력하세요. 예: "신규 주문"

![수신 웹훅 트리거 추가 화면](https://s3.amazonaws.com/cdn.freshdesk.com/data/helpdesk/attachments/production/155083668392/original/VefoDyP09gOZMgJCTXVj_tfDTJlnSAZZjw.png?1792418114)

### 3단계: 에이전트 지침 설정하기

AI 빌더에 들어온 데이터를 어떻게 쓸지 알려 주세요.

예를 들면 이렇게 쓸 수 있어요.

"웹훅으로 새 주문이 들어오면 고객의 이메일 주소로 고객을 찾고, 주문 내용을 담은 내부 메모를 만들어 줘."

외부 애플리케이션이 특정 필드 이름을 쓴다면 지침에 그 이름도 함께 적어 주세요. 예: `customer.email`

### 4단계: 웹훅 보안 설정하기

1. **수신 웹훅** 트리거 설정을 여세요.
2. 인증이 필요하면 **인증**에서 **공유 토큰 헤더**를 선택하세요.
3. 토큰을 생성하고 안전한 곳에 복사해 두세요.
4. 트리거 설정을 저장하세요.

인증을 켜면 요청을 보내는 애플리케이션이 요청 헤더에 토큰을 포함해야 해요.

![공유 토큰 헤더 인증 설정 화면](https://s3.amazonaws.com/cdn.freshdesk.com/data/helpdesk/attachments/production/155083668671/original/E5Lcjt3sjEcLomspnErlgLp2FsW2fUyrwg.png?1792418288)

### 5단계: 게시하고 웹훅 URL 복사하기

1. 에이전트와 트리거 설정을 저장하세요.
2. 에이전트의 지침을 다시 확인하세요.
3. 관리형 에이전트를 게시하세요.
4. **수신 웹훅** 설정을 여세요.
5. **웹훅 URL** 옆의 **복사**를 클릭하세요.

URL은 설정을 저장할 때 생성되고, 에이전트를 게시하면 사용할 수 있게 돼요.

### 6단계: 외부 애플리케이션 연결하기

외부 애플리케이션에서 다음 순서로 설정하세요.

1. 웹훅 또는 HTTP 요청 설정을 여세요.
2. 요청 방식으로 POST를 선택하세요.
3. 관리형 에이전트의 웹훅 URL을 붙여넣으세요.
4. 보낼 데이터를 설정하세요.
5. 인증을 켰다면 요청 헤더에 공유 토큰을 추가하세요.
6. 설정을 저장하세요.

자세한 단계는 외부 애플리케이션마다 달라요.

### 7단계: 웹훅 테스트하기

1. 외부 애플리케이션에서 테스트 요청을 보내세요.
2. **수신 웹훅** 설정으로 돌아오세요.
3. **마지막 요청**을 확인하세요.
4. 연결된 실행 내역이 있으면 열어 보세요.

{% hint style="warning" %}
메시지를 보내거나 CRM 기록을 수정할 수 있는 에이전트를 테스트할 때는 가상의 데이터나 테스트용 연락처를 사용하세요.
{% endhint %}

### 8단계: 실행 내역 확인하기

1. 관리형 에이전트의 **활동** 탭을 여세요.
2. **Webhook received**(웹훅 수신) 항목을 선택하세요.
3. 수신된 요청과 에이전트 결과를 확인하세요.
4. 필요하면 에이전트의 지침을 수정하세요.

![웹훅 실행 내역 확인 화면](https://s3.amazonaws.com/cdn.freshdesk.com/data/helpdesk/attachments/production/155083668509/original/pbLDfHfWE-nzGTPYWayc1uzEWslZ-MYfFg.png?1792418196)

## 자주 묻는 질문

### 관리형 에이전트에 수신 웹훅을 쓰려면 워크플로우가 꼭 필요한가요?
아니요. 트리거가 관리형 에이전트를 바로 실행해요.

### 외부 애플리케이션이 꼭 JSON으로 보내야 하나요?
아니요. JSON, 폼 데이터, XML, 일반 텍스트, 멀티파트 요청을 지원해요.

### 에이전트 하나에 웹훅 URL을 여러 개 만들 수 있나요?
네. 수신 웹훅 트리거마다 고유한 URL이 있어요.

### 공유 토큰 검증은 꼭 해야 하나요?
아니요. 선택 사항이에요. 다만 요청을 보내는 애플리케이션이 인증 헤더를 지원한다면 사용하는 것을 권장해요.

### 공유 토큰을 잃어버렸어요. 어떻게 하나요?
트리거 설정에서 토큰을 다시 생성하고, 외부 애플리케이션의 토큰도 새로 바꿔 주세요.

### 같은 요청이 두 번 전송되면 어떻게 되나요?
지원되는 중복 요청은 알아보고, 새 실행을 시작하지 않고 원래 실행을 반환해요.

### HTTP 202를 받으면 에이전트가 작업을 끝낸 건가요?
아니요. 요청이 접수되어 처리 대기열에 들어갔다는 뜻이에요.

### 에이전트 게시를 취소하면 어떻게 되나요?
해당 웹훅 URL이 더 이상 요청을 받지 않아요.

### 웹훅으로 받은 데이터는 어디에서 볼 수 있나요?
에이전트의 **활동** 탭에서 해당하는 **Webhook received**(웹훅 수신) 실행 내역을 선택하세요.
