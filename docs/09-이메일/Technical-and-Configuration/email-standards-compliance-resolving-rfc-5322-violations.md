# RFC 5322 규격 위반으로 이메일이 반송될 때 해결 방법

받는 쪽 서버가 RFC 5322 형식 규격에 맞지 않는 이메일을 거부하는 이유와, 이를 고치는 방법을 안내해요. 이메일이 "형식 오류"나 "표준 미준수" 같은 사유로 반송될 때 참고하세요.

## 어떤 문제인가요?

RFC 5322는 이메일 형식을 정한 공식 규격이에요. 이메일 헤더, 보내는 사람 주소, 메시지 구조가 이 규격에서 벗어나면 받는 쪽 서버가 이메일 전달 자체를 거부해요.

## 빠른 진단: RFC 5322 위반 여부 확인하기

반송 메시지는 보통 아래와 비슷해요.

- "From 헤더 또는 도메인이 필수 기술 표준을 충족하지 않아 이메일이 거부되었습니다"
- "프로토콜 또는 형식 문제로 메시지가 거부되어 연결이 거절되었습니다"
- "메일 루프 또는 과도한 홉(hop) 때문에 이메일 전송 표준을 위반하여 메시지가 거부되었습니다"
- "보내는 사람 주소 또는 메시지 형식이 이메일 표준에 맞지 않거나 받는 서버에서 허용되지 않습니다"
- "From 헤더가 없거나 잘못되었거나 허용되지 않는 문자가 있는 등, 이메일 메시지가 필수 형식 또는 헤더 표준을 충족하지 않습니다"
- "콘텐츠 또는 첨부파일이 Gmail의 보안 또는 콘텐츠 가이드라인을 위반하여 메시지가 차단되었습니다"
- "이메일 메시지 형식 또는 헤더가 필수 표준을 따르지 않습니다"
- "보내는 사람 주소 형식이 이메일 표준(RFC 5321/5322)을 따르지 않습니다"

## RFC 5322 규격 이해하기

RFC 5322가 정하는 내용은 다음과 같아요.

- 이메일 헤더의 구조와 형식 요건
- 올바른 보내는 사람 주소 형식과 사용할 수 없는 문자
- 메시지 전달 경로 규칙과 홉 수 제한
- 이메일 메시지의 필수 헤더 필드와 선택 헤더 필드
- 다국어 콘텐츠를 위한 문자 인코딩 표준

### 자주 발생하는 위반 유형

헤더 문제

- From 헤더가 없거나 형식이 잘못됨
- 보내는 사람 이름이나 주소에 잘못된 문자가 들어 있음
- 헤더의 날짜 형식이 올바르지 않음
- Received 헤더가 지나치게 많거나 형식이 잘못됨

주소 형식 문제

- 특수 문자가 제대로 인코딩되지 않음
- 이메일 주소를 감싸는 꺾쇠괄호(<>)가 없음
- 도메인 이름 형식이 잘못됨
- 표시 이름을 잘못 사용함

메시지 구조 문제

- 메일 루프 때문에 홉 수가 지나치게 많아짐
- 한 줄이 998자를 넘음
- 필수 메시지 경계(boundary)가 없음

## 단계별 해결 방법

### 1단계: 모든 발신자 설정 점검하기

1. 캠페인의 발신자 설정을 확인해요.
   - **마케팅 > 이메일 > 캠페인**으로 이동하세요.
   - 전달에 문제가 있는 캠페인을 각각 열어요.
   - 캠페인 안의 이메일 단계를 클릭하세요.
   - **보내는 사람**과 **보내는 이메일** 필드의 형식이 올바른지 확인하세요.
2. 워크플로우의 이메일 액션을 확인해요.
   - **자동화 > 워크플로우**로 이동하세요.
   - 이메일 액션이 들어 있는 워크플로우를 열어요.
   - 워크플로우의 **Send Email**(이메일 보내기) 액션을 하나씩 클릭하세요.
   - 보내는 사람 이름과 이메일 주소 설정을 확인하세요.
3. 일괄 작업의 이메일 설정을 확인해요.
   - **연락처 > 일괄 작업**으로 이동하세요.
   - 일괄 작업 설정의 보내는 사람 이름과 이메일 필드를 확인하세요.
   - 인증된 발송 도메인과 일치하는지 확인하세요.
   - 일괄 작업 이메일의 발신자 정보가 캠페인 기준과 같은지 확인하세요.
4. 모든 발신자 정보를 같은 기준으로 맞춰요.
   - 보내는 사람 이름에는 영문자·숫자, 공백, 기본 문장부호만 쓰세요.
   - 보내는 사람 이름에서 따옴표, 괄호, 기호 같은 특수 문자는 지우세요.
   - 이메일 주소는 특수 문자 없이 name@domain.com 형식으로 쓰세요.
   - 표시 이름은 64자 미만으로 하세요.
   - 모든 이메일 발송 경로에서 보내는 사람 이름 형식을 똑같이 유지하세요.
   - 모든 보내는 이메일 주소가 제대로 인증되어 있는지 확인하세요.
   - 회신 주소가 유효하고 형식이 올바른지 확인하세요.

{% hint style="info" %}
발신자 설정이 제대로 되었다면 다음과 같은 상태예요.

- 모든 캠페인의 보내는 사람 주소가 올바른 이메일 형식을 따릅니다.
- 워크플로우 이메일 액션이 일관되고 규격에 맞는 발신자 정보를 쓰세요.
- 일괄 작업 이메일의 형식과 구조가 올바릅니다.
- 모든 이메일 발송 경로에서 표시 이름에 표준 문자만 쓰고 있어요.
{% endhint %}

### 2단계: 이메일 템플릿 구조 확인하기

1. 이메일 템플릿을 열어요.
   - **마케팅 > 이메일 > 템플릿**으로 이동하세요.
   - 전달에 문제가 있는 템플릿을 여세요.
2. 템플릿의 규격 문제를 고쳐요.
   - 한 줄이 998자를 넘지 않는지 확인하세요.
   - 여러 이메일 클라이언트에서 템플릿을 테스트하세요.

### 3단계: 외부 검증 도구 사용하기

1. Mail-Tester.com을 사용해요.
   - 캠페인, 워크플로우, 일괄 작업에서 Mail-Tester.com이 알려 주는 주소로 테스트 이메일을 보내세요.
   - 상세한 규격 준수 리포트를 확인하세요.
   - 리포트에 나온 RFC 5322 위반 사항을 고치세요.
2. MXToolbox Email Header Analyzer를 사용해요.
   - 정상 전달된 메시지에서 이메일 헤더를 복사하세요.
   - 헤더 분석 도구에 붙여 넣으세요.
   - 규격 준수 경고와 오류를 확인하세요.
3. RFC 5322 검증 도구를 사용해요.
   - 온라인 RFC 준수 검사기를 이용하세요.
   - 연락처를 가져오기 전에 이메일 주소 형식을 검증하세요.
   - 메시지 구조가 표준을 지키는지 테스트하세요.

## 복구 일정과 예상 결과

| 단계 | 작업 | 예상 결과 |
| --- | --- | --- |
| 1단계: 즉시 수정(1~2시간) | 캠페인, 워크플로우, 일괄 작업 전체에서 보내는 사람 주소 형식 수정 | RFC 규격 위반으로 인한 반송이 바로 줄어듭니다 |
| 2단계: 템플릿 최적화(2~4시간) | 모든 이메일 템플릿의 구조를 검토하고 수정 | 메시지 형식 위반이 사라집니다 |
| 3단계: 검증 및 테스트(1~2일) | 모든 이메일 발송 방식에서 종합 테스트 | RFC 규격 문제 없이 꾸준히 전달돼요 |

## 예방을 위한 권장 사항

지속적으로 점검하기

- 정기 발신자 점검: 캠페인, 워크플로우, 일괄 작업의 발신자 정보를 매월 확인하세요.
- 템플릿 검증: 템플릿을 사용하기 전에 규격에 맞는지 확인하세요.
- 외부 테스트: Mail-Tester.com으로 매주 테스트해서 문제를 일찍 찾아내세요.
- 반송 모니터링: 전달 리포트에서 RFC 규격 오류가 반복되는지 살펴보세요.

설정 기준 지키기

- 일관된 발신자 정보: 모든 이메일 발송 경로에서 같은 규격 준수 발신자 정보를 쓰세요.
- 표준 문자 사용: 보내는 사람 이름과 표시 이름에 특수 문자를 쓰지 마세요.
- 올바른 이메일 형식: 항상 유효한 이메일 주소 형식을 사용하세요.
- 템플릿 규격 준수: 모든 HTML 템플릿이 RFC 표준을 지키는지 확인하세요.

## 문제가 계속되나요?

RFC 5322 규격 문제가 계속되면 다음 순서로 확인해 보세요.

1. 오류를 구체적으로 기록하세요. 반송 메시지 내용을 그대로 모으고, 어떤 발송 방식에서 발생했는지 확인하세요.
2. 하나씩 테스트하세요. 캠페인, 워크플로우, 일괄 작업에서 각각 따로 테스트 이메일을 보내세요.
3. 최근 변경 사항을 확인하세요. 발신자 정보나 템플릿을 수정한 적이 있는지 살펴보세요.
4. 설정을 서로 비교하세요. 플랫폼 안의 모든 이메일 발송 방식에서 설정이 일관되는지 확인하세요.

## 자주 묻는 질문

### RFC 5322가 정확히 무엇인가요?
RFC 5322는 이메일 메시지의 구조, 즉 헤더, 보내는 사람 주소 형식, 전체 메시지 문법을 정한 인터넷 표준이에요. 메일 서버는 메시지를 받기 전에 이 표준에 맞는지 검사해요.

### 일괄 작업도 캠페인과 같은 발신자 형식을 써야 하나요?
네. 캠페인, 워크플로우 이메일 액션, 일괄 작업은 각각 자기만의 메시지 헤더를 만들어요. 그래서 발송 방식마다 올바른 형식의 인증된 발신자 정보를 따로 써야 해요.

### 표시 이름의 특수 문자 때문에 하드 바운스가 생길 수 있나요?
네. 표시 이름에 이스케이프 처리되지 않은 따옴표, 괄호, 기호가 있으면 From 헤더의 형식이 깨질 수 있어요. 일부 받는 서버는 형식이 잘못된 헤더를 해석하려 하지 않고 메시지 전체를 거부해요.

### 전체 목록에 보내기 전에 규격 준수 여부를 테스트하려면 어떻게 하나요?
실제로 쓰려는 캠페인, 워크플로우, 일괄 작업에서 Mail-Tester.com이나 헤더 분석 도구로 테스트 이메일을 한 통 보내세요. 지적된 항목을 먼저 고친 뒤에 전체 연락처 목록에 발송하세요.

### 캠페인 하나의 발신자 정보만 고치면 RFC 문제가 모두 해결되나요?
꼭 그렇지는 않아요. 규격 문제는 보통 이메일을 만든 발송 방식에 따라 달라요. 캠페인, 워크플로우, 일괄 작업을 각각 확인하고 따로 고쳐야 해요.

### SPF나 DKIM 인증 실패와 같은 문제인가요?
아니요. 인증 문제는 도메인이 이 메시지를 보낼 권한이 있음을 증명하는 것과 관련돼요. RFC 5322 규격은 메시지 자체의 구조가 올바른지에 대한 문제예요. 인증이 완벽해도 헤더 형식이 잘못되면 거부될 수 있어요.
